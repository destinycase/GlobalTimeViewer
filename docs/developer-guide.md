# Global Time Viewer 개발자 가이드

이 문서는 현재 소스 트리의 구조와 실행 계약, 검증·배포·문서 관리 절차를 설명합니다. 프로그램은 단순한 정적 HTML 페이지가 아닙니다. 일반적인 ES 모듈 import 대신 전역 `GTV...` API와 순서가 지정된 스크립트 로더를 사용하는 브라우저 확장이므로, 파일 분리나 로드 순서를 바꾸기 전에 관련 경계를 먼저 이해해야 합니다.

**기준:** 소스 구조와 현재 안정 버전 모두 v3.17.1(6차 안정 버전)입니다. 이 문서는 변경할 때 지킬 규칙과 절차를 다룹니다. 실행 흐름·모듈 관계도·기능별 시작 파일·기능별 구현 메모는 [코드 구조 안내](code-navigation.md), 모듈별 실제 API와 전역 의존성은 [생성 인벤토리](module-dependency-inventory.md), 용어는 [용어 사전](Glossary.md)을 함께 참고하세요.

## 2. 런타임 흐름과 로드 순서

`src/index.html`이 생성 로더(`js/source-script-loader.js`)를 불러오면, 로더가 `src/runtime-script-list.txt`에 적힌 순서대로 스크립트를 넣어 각 모듈이 전역 `GTV...` API를 등록합니다. 목록 끝의 `main.js`가 모듈을 확인해 서비스를 조립하고 `GTVMainAppBootstrap`이 앱을 시작합니다. 비동기 병렬 로드가 아니라 전역 등록 순서가 의미 있는 로드이며, 배포 빌드는 같은 목록을 하나의 축약 번들(`js/bundle.js`)로 합칩니다. 단계별 흐름과 관계도는 [코드 구조 안내 1~2장](code-navigation.md#1-실행-흐름)에 있습니다.

런타임 파일을 추가/이동하거나 스크립트 순서를 바꾸는 변경은 아래를 한 묶음으로 다룹니다.

1. 적절한 도메인 소유 모듈에 구현하고 필요한 전역 API 계약을 정합니다.
2. `src/js/modules/main-module-spec.js`의 계약 선언 및 이에 해당하는 조립 지점을 확인합니다.
3. `src/runtime-script-list.txt`에서 의존 관계에 맞는 위치에 등록합니다.
4. `npm run sync:source-loader`로 생성 로더를 갱신합니다. 생성 파일을 수동으로 고치지 않습니다.
5. 모듈 API나 의존성이 바뀌었으면 `npm run docs:module-inventory`로 인벤토리를 다시 만듭니다.
6. 로더 검사, 해당 모듈 테스트, 동작 회귀 검사 및 빌드를 실행합니다.

## 3. 아키텍처와 책임 경계

### 모듈 API와 의존성 전달

대부분의 런타임 모듈은 IIFE 내부에서 `createService(deps = {})` 형태의 서비스를 만들고, 전역에 모듈 API를 등록합니다. 인스턴스별 deps 전달이 테스트 대역과 실행 환경 차이를 수용하는 경계입니다. 새 기능의 구현은 책임을 가진 도메인 모듈에 두고, 조립 파일에는 의존성 전달과 API wiring만 둡니다.

일반적으로 모듈 API는 불변 객체로 공개됩니다. 기존 API 반환 형식과 전역 이름을 바꾸면 resolver, 조립 서비스, 테스트와 호환 호출자가 동시에 영향을 받을 수 있습니다. 공개 API 변경은 단일 파일 리팩터링처럼 취급하지 말고 모든 소비자와 테스트를 추적하세요.

### 조립 계층과 main.js

`main.js`는 규모가 크더라도 단순히 줄 수를 줄이기 위해 분해하면 안 됩니다. 여러 초기 상태, 호스트/브라우저 접근, 공개 전역 호환 함수 및 조립 순서가 모여 있는 곳입니다. 비슷한 코드라는 이유만으로 상태 소유권이나 호출 순서를 작은 파일들에 복제하면 추적해야 할 연결 지점이 늘어납니다.

기능별 책임은 도메인 모듈에 둡니다. 조립은 `main-runtime-*-bootstrap.js`와 config builder·composition 계열이 맡습니다. 예전에는 모듈 하나를 만들어 형태만 확인하는 `*-bindings.js` 파일이 모듈마다 있었지만 지금은 두 공용 도우미로 대신합니다.

- `GTVServiceInvokeUtils.createRequiredModuleService(모듈, 이름, deps, 필수 메서드, 오류 문구)`: 모듈 API를 확인하고 서비스를 만든 뒤 필요한 메서드가 있는지 검사합니다.
- `GTVServiceInvokeUtils.createLateBoundForwarders(getService, 이름, 메서드 목록)`: 나중에 만들어지는 서비스를 호출할 때 찾아 부르는 함수 묶음을 만듭니다. 서비스가 없으면 `Missing required module API: <이름>.<메서드>` 오류를 냅니다.

남은 `*-bindings.js`(`main-global-bindings`, `main-facade-bindings`, `main-runtime-public-api-bindings`)와 accessor proxy 4개(`bootstrap`, `core`, `operation`, `ui-bridge`)는 인수 기본값, 대체 처리, 여러 서비스 조합 같은 실제 동작을 가집니다. `main-runtime-reference-accessors.js`는 나중에 정해지는 서비스·상태를 읽는 함수 80개를 표 하나로 정의합니다. 변경 전 [코드 구조 안내](code-navigation.md)의 `main.js` 연결 지점과 관계도를 보고, 새 파일이 실제로 응집도나 테스트 경계를 높이는지 확인하세요. 크기만 작은 공용 util 모듈을 추가하지 않습니다.

### 기능 영역별 소유 모듈

기능 영역마다 책임을 가진 모듈 계열과 경계에서 확인할 것은 [코드 구조 안내 3장](code-navigation.md#3-기능별-모듈과-시작-파일)의 표에 있습니다. 새 기능은 그 표의 소유 모듈에 둡니다.

## 4. 상태와 저장 데이터

- 핵심 실행 상태는 조립 계층이 소유하고, 각 도메인 서비스에는 필요한 읽기/쓰기 함수가 전달됩니다. 같은 상태의 별도 사본을 UI 모듈에 장기간 보유하면 화면과 저장 데이터가 어긋날 수 있습니다.
- 앱 상태 patching, 그룹 컨텍스트, 사용자 환경설정, 복사/표시 형식은 각각의 소유 모듈 경로를 통해 변경합니다. 이미 있는 updater/normalizer 경로를 우회해 직접 전역을 바꾸지 마세요.
- 저장소 접근은 `state-persistence.js`가 맡고, **저장 위치는 확장 출처(origin)의 `localStorage` 하나**입니다. `manifest.json`에 `storage` 권한을 두지 않으므로 `chrome.storage`는 쓰지 않습니다. 저장 데이터는 `revision`, `updatedAt`, `data`로 감쌉니다. 읽기·쓰기 함수(`getStorageValue`, `setStorageValue`, `savePersistence`, `loadPersistence` 등)는 호출하는 쪽과의 약속대로 비동기(Promise) 함수로 유지합니다. 쓰기는 큐로 차례대로 처리하므로 나중에 요청한 저장이 마지막에 남습니다.
- 현재 핵심 데이터 키는 `GTV_v324_Data`이고 구버전 키 목록은 `app-config.js`가 선언합니다. 테마, 언어, UI 배율은 별도 키(`GTV_Theme`, `GTV_Lang`, `GTV_UIScale`)입니다. 실제 저장 구조를 바꾸려면 normalizer, 마이그레이션/legacy fallback, 설정 내보내기/가져오기, 테스트를 함께 검토합니다.
- 시간대 항목 정리, 서머타임 표시, 시각 입력 보정의 현재 구현은 [코드 구조 안내 4장](code-navigation.md#시간대-데이터와-서머타임)에 있습니다.
- 설정 가져오기는 외부 JSON 입력이므로 `settings-io.js`와 `data-transfer.js`의 검증·정규화·저장 실패 경로를 건너뛰지 않습니다. 개별 그룹/보조 그룹 가져오기를 전체 설정 가져오기와 같은 payload로 가정하지 마세요.

## 5. 안전한 변경 절차

1. **현행 구현을 찾습니다.** 먼저 [코드 구조 안내](code-navigation.md)를 보고 생성 인벤토리에서 모듈의 API, 입력, 소비자를 확인합니다.
2. **변경 책임을 고릅니다.** 기능 동작은 소유 도메인에, 조립 변경은 기존 composition/bootstrap에, 사용자 안내/표시는 UI 경계에 둡니다. 단지 분리를 위한 새 파일을 만들지 않습니다.
3. **계약을 기록합니다.** 함수 입력/반환, 비동기 여부, 상태 변경 소유자, 전역 API 및 저장 payload가 달라지는지 먼저 확인합니다. 핵심 기능과 데이터 결과를 바꾸는 UX 수정은 별도 동작 변경으로 검토해야 합니다.
4. **최소 범위로 수정합니다.** 직접 관련 소비자만 바꾸고 fallback/오류 흐름을 보존합니다. 사용자 문자열은 `src/i18n.js`의 한국어/영어 양쪽에 추가합니다.
5. **검증합니다.** 7장의 명령을 실행하고 변경한 도메인의 기존 테스트를 확인합니다. 저장, 날짜 경계, 시간대/서머타임, 가져오기 입력이라면 경계 사례 테스트가 필요합니다.
6. **버전·이력·문서를 갱신합니다.** 제품 동작을 바꿨으면 7장의 버전 규칙에 따라 패치 버전을 올리고 [개발 이력](development-history.md)에 기능 변경을 적습니다. 동작은 같고 배포 번들이 바뀌는 구조 정리(리팩터링)도 패치 버전을 올리고 개발 이력에 "구조 정리" 항목으로 적습니다. 구조/모듈 계약이 바뀌면 이 가이드, 코드 구조 안내, 인벤토리 중 영향받는 곳을 같은 작업에서 반영합니다.

### 특히 피할 변경

- 기존 전역 API를 검토 없이 삭제/이름 변경하거나 모든 파일을 ES module로 한 번에 바꾸기
- `src/runtime-script-list.txt`와 생성 로더 사이의 불일치 또는 로드 순서 의존성 깨뜨리기
- `main.js` 상태/호환 경계를 기능별 작은 파일에 중복 분산하기
- 의미 있는 응집 없이 지나치게 작은 모듈 또는 모든 기능을 빨아들이는 공용 util 파일 만들기
- 가져오기 데이터를 정규화기/검증기 우회해서 저장하거나 기존 저장 키 호환성을 제거하기
- UI 문자열을 하드코딩해 두 언어가 서로 달라지게 만들기
- 계산 또는 데이터 출력을 바꾸는 수정인데 화면 문구 변경으로만 취급하기
- 오류를 무시하는 광범위한 catch 또는 정상 오류를 `console.log`로 숨기기

## 6. 코딩 컨벤션

현재 ESLint 설정(`eslint.config.cjs`)을 최종 기준으로 합니다.

- JavaScript 코드는 `"use strict"`를 사용하고 동등 비교는 `===`/`!==`로 작성합니다.
- 정의되지 않은 변수, 중복 선언/키, 도달 불가능 코드, 부동소수점 정밀도 손실, `debugger`를 허용하지 않습니다.
- `console.log`는 금지되어 있습니다. 필요한 진단은 목적이 명확한 `console.warn` 또는 `console.error`로 남깁니다.
- `src/js/modules/`에서는 사용하지 않는 변수 검사가 적용됩니다. 의도적으로 사용하지 않는 매개변수는 기존 명명 규칙(`_` 접두사)을 따릅니다.
- 모듈은 의존성을 인자로 받고 가능한 경우 DOM/브라우저 전역을 직접 참조하지 않아 테스트에서 대체 가능하게 합니다. 다만 기존 소유권 패턴과 충돌하는 신규 추상화를 만들지는 않습니다.
- 의존성 함수를 감싸는 공통 코드는 모듈마다 새로 쓰지 않고 `service-invoke-utils.js`(`GTVServiceInvokeUtils`)의 함수를 씁니다. `createDependencyLogger(deps, "warn"|"error", globalObj)`는 주입된 로거와 콘솔 순서로 기록하고, `createSafeCallableFactory("GTV모듈명", log)`는 없는 의존성을 빈 함수로, 예외는 `[GTV모듈명] Dependency "이름" threw.`로 기록합니다. `pickSafeCallables(deps, keys, toSafeCallable)`는 의존성 목록을 한꺼번에 감쌉니다. 모듈 생성·확인과 나중에 만들어지는 서비스 호출은 3장의 `createRequiredModuleService`, `createLateBoundForwarders`를 씁니다. 단위 검사는 `tests/helpers/install-runtime-globals.mjs`(Vitest 설정)가 이 도우미를 설치합니다.
- 사용자 입력/가져오기 입력은 정규화와 검증 경로를 사용합니다. 생성 HTML에 사용자 값을 넣을 때는 기존 escaping 패턴을 따르고, 단순 텍스트는 DOM `textContent`를 우선합니다.
- 새 화면 문구는 한국어/영어 번역 키를 함께 추가하고 버튼/툴팁은 키 연결(`data-i18n`, `data-i18n-title`)을 확인합니다.
- 저장 실패/선택 기능 fallback과 필수 초기화 오류는 서로 다른 상황입니다. 전자는 기존 fallback과 사용자 피드백을 보존하고, 후자는 fatal error 흐름을 숨기지 않습니다.
- `src/style.css`는 맨 위 목차와 `§01`~`§23` 구역 머리 주석으로 나뉩니다(테마 변수, 컨트롤 패널, 시간 표, 타임라인, 계산기, 모달, DatePicker 등). 새 규칙은 해당 구역에 넣고, 밝은 테마 덮어쓰기(`:root[data-theme="light"]`)는 바꾸는 규칙 바로 옆에 둡니다. 구역을 새로 만들면 목차도 함께 고칩니다. 설정·도움말 팝업 스타일은 `§17`, 사이드바 아이콘 버튼은 `§16`에 있습니다. `§22 Visual hierarchy refinements`는 버튼 강조 단계·구분선·토글·타임라인 색·입력칸·표 정리를 항목별로 모아 앞 구역의 규칙을 덮어쓰며, 밝은 테마 덮어쓰기도 각 항목 안에 둡니다.
- 팝업·확인 창·툴팁·타임존 추가·계산기 배치처럼 여러 모듈이 함께 움직이는 기능의 현재 구현은 [코드 구조 안내 4장](code-navigation.md#4-기능별-구현-메모)에 적습니다. 그런 기능의 구현을 바꾸면 그 메모를 같은 작업에서 고칩니다.
- 텍스트 파일은 UTF-8, LF 줄바꿈으로 고정합니다(`.gitattributes`, `.editorconfig`). 포맷 변경 diff가 실제 코드 변경과 섞이지 않도록 주의합니다.

## 7. 개발 환경·검증·배포

### 브랜치와 태그

소스 작업과 GitHub 기본 브랜치는 `main`입니다. CI는 `main`에 대한 푸시와 풀 리퀘스트에서 lint, 인벤토리 검사, 커버리지 포함 전체 검사를 실행한 뒤 패키징을 검증합니다. 패키징 작업은 앞의 검사가 통과한 뒤에만 시작하므로 패키징 안의 사전 검사는 CI에서만 건너뛰며(`GTV_SKIP_PRETEST=1`, CI가 아닌 곳에서는 거부), 만든 ZIP을 GitHub 결과물(artifact)이나 Release로 올리지 않습니다. 실행 환경은 버전을 고정한 Windows 러너입니다.

안정 버전 태그(`vX.Y.Z`)는 같은 버전의 기준판 문서(`docs/master-baseline-vX.Y.Z.md`)와 짝을 이루며 모두 보존합니다. 문서 최신화를 이유로 태그를 옮기지 않습니다. 지금 있는 안정 버전은 [README의 문서 안내](../README.md#문서-안내)에서 확인합니다.

### 준비와 빌드

Node.js 버전은 `.nvmrc`(24.14.0)를 따릅니다.

```sh
npm ci
npm run build
```

`npm run build`는 스크립트 목록 검증 → 번들 결합·축약(크기 한도 950KB) → Vite 빌드 → 배포 폴더 구성 순으로 `dist_extension/`을 만듭니다. Chrome의 `chrome://extensions`에서 개발자 모드를 켜고 `dist_extension/`을 불러와 확인합니다. `npm run build:strict`는 버전 불일치를 자동 수정하지 않고 실패시킵니다. Windows에서 npm.ps1이 차단되면 `npm.cmd`·`npx.cmd`를 사용할 수 있습니다.

### 검증 종류

| 명령 | 내용 |
| --- | --- |
| `npm run lint` | ESLint(경고 0) |
| `npm test` | 단위·통합 검사(`tests/unit`, `tests/integration`). 감시 모드는 `npm run test:watch` |
| `npm run test:coverage` | 단위·통합 검사 + 커버리지 기준(구문·줄 83%, 분기 72%, 함수 70%) |
| `npm run docs:module-inventory:check` | 체크인된 모듈 인벤토리가 소스와 일치하는지 확인 |
| `npm run test:package` | 배포물 검사(`tests/audit`). 현재 버전의 `release/gtv-vX.Y.Z.zip`이 없으면 건너뜀(skip)으로 표시 |
| `npm run ci:gate` | lint → 인벤토리 검사 → 커버리지 → strict build |
| `npm run verify:chrome` | 실제 Chrome 검사(로컬 필수, CI 제외). strict build 후 `dist_extension/`과 `release/gtv-vX.Y.Z.zip` 추출본을 헤드리스 Chrome에 로드해 확인 |
| `npm run package` | 배포 ZIP 생성과 배포물 검사(아래) |

배포물 검사는 ZIP의 이름과 매니페스트·번들 버전, 필수 파일, 매니페스트와 `index.html`이 가리키는 파일의 존재, 소스·테스트·개발 파일과 숨김 파일의 미포함, LF 줄바꿈, 개발 환경 값(Git 사용자 정보, 홈·작업 폴더 경로)의 노출 여부, `dist_extension/`과의 파일 단위 일치를 확인합니다. 건너뜀이 있으면 통과로 세지 않습니다.

#### 검사 파일의 위치

| 위치 | 내용 |
| --- | --- |
| `tests/unit/` | 모듈 단위 검사. 파일 하나가 `src/` 모듈 또는 스크립트 하나를 대상으로 합니다(`*-module.test.mjs`). |
| `tests/integration/` | `main.js` 조립·전역 API·런타임 흐름·로더 동기화·i18n 무결성처럼 여러 모듈을 함께 실행하는 검사 |
| `tests/audit/` | 배포 ZIP 검사 |
| `tests/helpers/` | 검사 공용 도우미(`main.js` 실행 샌드박스 등) |
| `tests/chrome/` | 실제 Chrome 검사 실행기(`verify-chrome.mjs`)와 CDP 도우미(`cdp-client.mjs`) |
| `tests/local/` | 검수자 전용 도구(Git·자동 검사 제외) |

#### 실제 Chrome 검사

`npm run verify:chrome`은 외부 자동화 라이브러리 없이 Chrome DevTools Protocol을 Node 내장 WebSocket으로 직접 사용합니다. 대상마다 새 프로필의 헤드리스 Chrome을 띄워 확장을 로드합니다. Chrome 경로는 `GTV_CHROME_PATH` 환경 변수나 기본 설치 위치에서 찾습니다. 확인 항목은 아래와 같습니다.

1. 확장 로드, 서비스 워커 시작, 아이콘 클릭 처리기 등록
2. 앱 초기화(치명 오류 화면 없음, 콘솔 오류 없음, 버전 표시)
3. 본 화면에 도시 콤보박스가 없고 `타임존 추가` 이름표가 있는지, `목록` → 팝업의 `사용자 커스텀` 탭(목록·검색 숨김, 약어 칸 초점)에서 사용자 지정 시간대를 추가하면 팝업이 닫히고 저장되어 다시 열어도 유지되는지, 추가 후나 입력 중 닫은 뒤 다시 열면 입력칸이 비고 시차가 +00:00인지
4. 시간 변경 탭 입력 → 다른 행 시각 반영
5. 고정 시간 탭 렌더, 타임라인 슬롯 드래그 후 저장값 유지
6. 계산기 기간 계산과 날짜 바꾸기
7. 설정 내보내기 파일 생성과 내용
8. `localStorage`의 옛 저장 키 이어받기
9. 예전 버전이 고정 시차로 저장한 서머타임 도시가 계절에 맞는 시차로 바뀌고, 서머타임인 시각 옆에만 `DST` 표시가 나오는지
10. 고정 시간 탭에 고정 날짜 칸이 없고, 옛 저장의 고정 날짜를 무시하고 저장에서 빼며, 탭을 연 날(기준 시간대 오늘)의 각 슬롯 시각에 브라우저 시간대 정보와 같은 `DST` 표시와 시간대 약어·UTC 시차가 나오는지
11. 서머타임 경계를 걸친 기간이 모든 행에서 실제 경과 시간인지, 변환기가 없는 날짜를 거부하는지, 날짜 이동이 소수 이동량을 안내와 함께 거부하는지
12. 변환기 칸에 실제 키로 한 글자씩 입력해도 변환되는지, 카운트다운 수동 수정, 서머타임 시작의 없는 시각 보정과 안내, 고정 시간 칸의 범위 밖 시각 거부, 타임존 프리셋 검색 안내(도시·약어·UTC 오프셋)
13. 그룹 추가 버튼을 실제 마우스로 눌러 이름을 넣으면 새 그룹이 만들어져 선택·저장되고 다시 열어도 남는지(취소하면 그대로인지), 같은 도시를 다시 추가하면 안내와 함께 거부되는지. 그룹 이름은 화면 안 입력 창으로 물어야 하며, 브라우저 기본 입력 창이 뜨면 실패로 판정합니다. 그룹을 고른 뒤 왼쪽 탭(시간 변경·실시간·연속 시간·고정 시간)을 오가도 같은 그룹이 선택되어 있는지도 확인합니다. 타임존 추가 팝업의 탭이 `타임존 프리셋`(먼저 열림, 첫 타일 `표준시 (UTC)`)과 `사용자 커스텀` 두 개이고 Esc로 닫히는지, `표준시 (UTC)` 타일이 UTC 행이 보이면 안내만 하고 숨겨져 있으면(기준 시간을 바꾸고 UTC 행 삭제) 다시 표시하며 시간대를 추가하지 않는지도 확인합니다
14. 창 너비 1280px·1600px에서 연속 시간 변경 표(서머타임 표시가 있는 행 포함)의 모든 요소가 자기 칸 안에 있고 입력값·글자가 잘리지 않으며 표가 옆으로 넘치지 않는지, 시간 포맷 변환기의 모든 값이 잘리지 않는지, 같은 패널의 시간 조정 줄들이 시간·일·주 버튼을 같은 위치에 두는지(다른 탭에서 125% 크기로 시작한 경우 포함), 1600px에서 시간 변경 표가 옆으로 넘치지 않고 시각이 잘리지 않는지, 계산기 날짜(시작일·종료일·기준일)가 달력 버튼과 한 줄이고 잘리지 않으며 기간 계산이 한 줄인지(125% 크기에서는 종료일 줄바꿈 허용, 잘림·버튼 분리는 실패), 날짜 이동의 단위·방향 선택칸이 가장 긴 항목을 다 보여 주고 카드 안에 있는지, 도구 줄이 `타임존 추가`로 시작해 실시간·시간 변경 탭(1600px에서는 고정 시간 탭도)에서 한 줄로 패널 안에 있고 예전 타임존 줄·콤보박스가 없는지, 팝업 커스텀 탭의 시·분 선택칸 폭이 같고 값이 화살표에 가리지 않는지, 고정 시간 탭에 고정 날짜 칸이 없고 `실시간 표시` 묶음이 보이며 글자가 다른 이름표와 같은 형식인지
15. 설정·도움말·그룹 설정 버튼에 마우스를 올려 툴팁을 띄운 뒤 눌러 연 팝업을 닫기 버튼이나 Esc로 닫아도 툴팁과 버튼 강조가 남지 않고(초점은 버튼으로 돌아옴) Tab으로 이동하면 툴팁이 나오는지, 사이드바 아래쪽에 도움말·설정 아이콘 버튼만 왼쪽 정렬로 있는지, 실제 클릭으로 설정 팝업이 열리고 그 안에 UI 크기·테마·언어·내보내기·가져오기·초기화 항목이 있으며 팝업 안에서 테마를 바꿀 수 있는지, Esc로 닫히고 초점이 버튼으로 돌아오는지, 도움말 팝업이 열리고 바깥 클릭으로 닫히는지, 설정 팝업에서 초기화 확인이 화면 안 확인 창으로 뜨고 취소·Esc면 설정 팝업이 남고 확인하면 닫히는지(브라우저 기본 창이 뜨면 실패), 고정 시간 슬롯 이름을 화면 안 입력 창으로 바꾸고 저장되는지, 사이드바 제목 아래 구분선이 보이고 버전 표기가 제목 영역 오른쪽 끝에 맞춰 있는지
16. 선택한 그룹 탭에 이름과 설정 버튼만 있고 기본 화면에 기준 시간·낮/밤 선택이 없는지, 설정 버튼을 실제 클릭해 그룹 설정 팝업이 열리고 제목에 그룹 이름이 나오는지, 팝업에서 바꾼 기준 시간·낮/밤 시간이 그 그룹에만 저장되고 다른 그룹은 공통 값을 쓰는지, 이름은 입력만으로 저장되지 않고 `변경` 버튼으로 저장되는지, Esc로 닫히는지, 그룹 삭제 확인에서 취소하면 그대로이고 확인하면 지워지는지
17. v3.16.10까지의 형식(내부 시간대 `UTC`+고정 시차)으로 저장된 표준시 항목이 같은 id의 고정 시차 항목으로 바뀌어 표에 나오고 시각이 맞는지(UTC 00:00 → 09:00), 사용자 커스텀에서 -11:00 항목을 추가하면 표에 나오고 시각이 맞는지(→ 전날 13:00), 다시 열어도 남고 영어 화면에서 `Standard Time`으로 보이는지
18. 고정 시간 탭에서 `실시간 표시`를 끄고 타임라인을 켠 상태로 `표준시 (UTC)` 타일로 숨긴 UTC 행을 다시 표시하거나 도시를 추가하면, 표와 타임라인에 그 행이 바로 나오는지, 타임존 추가 팝업이 실제 마우스로 팝업 안을 클릭하면 열린 채이고 바깥을 클릭하면 닫히는지

결과는 `scratch/chrome/<시각>/result.json`에 남습니다. 실제 툴바 아이콘 클릭이나 화면을 보고 판단하는 항목은 자동 검사 범위 밖입니다. `GTV_CHROME_SKIP_BUILD=1`이면 이미 만든 `dist_extension/`을 그대로 검사하고, `GTV_CHROME_TARGETS=dist` 또는 `zip`으로 대상을 고를 수 있습니다.

모든 검사는 명령 하나로 사람 개입 없이 끝나고 스스로 통과/실패를 판정해야 합니다. 사람이 클릭·확인해야 하는 검사나 장시간 검사는 만들지 않으며, 자동으로 확인할 수 없는 범위는 내부 보고서에 미검증 범위로 적습니다. 검사 결과·로그·임시 빌드는 `scratch/`에 둡니다.

### 배포 ZIP 만들기

```sh
npm run package
```

1. 회귀 검사(`npm test`)
2. 엄격 빌드(`npm run build:strict`) → `dist_extension/`
3. 빌드 결과의 매니페스트 버전 확인
4. `release/gtv-vX.Y.Z.zip` 생성. 같은 이름의 ZIP이 있으면 덮어쓰지 않고 중단합니다.
5. ZIP을 다시 읽어 `dist_extension/`과 파일 단위로 대조하고 배포물 검사를 실행한 뒤 크기와 SHA-256을 출력합니다.

ZIP 항목은 이름순으로, 고정된 시각·권한 값으로 기록하므로 같은 소스에서 다시 만들면 같은 SHA-256이 나옵니다. 중간 검증이나 재현성 확인은 `GTV_RELEASE_DIR=scratch/...`로 출력 폴더를 분리합니다.

### 버전과 배포 완료 기준

제품 동작을 바꾸면 패치 버전을 정확히 1 올리고 `package.json`·`package-lock.json` 루트·`manifest.json`(`version`, `version_name`)·`src/js/modules/app-config.js`·README를 맞춥니다. 같은 논리적 작업은 한 버전으로 묶고 메이저·마이너 변경은 별도 지시에 따릅니다. 문서·테스트·검증 도구·폴더 구조만 바꾸면 버전을 올리지 않습니다.

[개발 이력](development-history.md)에는 기능 추가·개선·제거, 사용자에게 영향을 주는 동작 변경, 코드 구조 정리(리팩터링)를 해당 버전에 적습니다. 항목마다 앞에 분류를 대괄호로 하나 붙이고(예: `- **[개선]** 내용`, 분류는 추가·개선·수정·제거·구조 정리), 분류가 섞이면 항목을 나눕니다. 구조 정리는 무엇을 정리했는지 짧게 적고 동작이 바뀌지 않음을 밝힙니다. 웹 스토어 제출 기준이 되는 안정 버전은 기능 변경이 없어도 지정 사실과 기준판 문서 링크를 남깁니다. 안정 버전 지정과 실제 스토어 제출·게시 완료는 구분합니다. 검증 결과·조사·문서 정리·커밋·ZIP 생성 기록은 `docs_dev/`에 남깁니다.

제품 작업은 필요한 검사, 배포 ZIP 생성과 배포물 검사, 이력과 로컬 커밋까지 확인합니다. 실패가 남으면 배포 완료로 보고하지 않습니다. 문서만 바꿨을 때 검증된 같은 버전 ZIP을 다시 만들지 않습니다.

`release/`의 로컬 ZIP과 원격 푸시·GitHub Release·웹 스토어 제출은 별개이며, 외부 공개는 별도 요청으로 수행합니다. `release/`에는 모든 안정 버전 ZIP과 마지막 안정 버전 이후에 만든 ZIP만 둡니다. 새 안정 버전을 선언하면 직전 안정 버전과 새 안정 버전 사이의 ZIP을 지웁니다. 지운 버전은 Git 커밋에서 다시 빌드할 수 있고, 파일 지문은 내부 보고서에 남깁니다. 웹 스토어에는 안정 버전 ZIP만 제출합니다.

사용자 가이드는 새 안정 버전이 선언될 때 그 버전 기준으로 다시 맞추며, 과거 버전 표현은 넣지 않습니다. 공개 문서에는 민감한 URL·인증 값을 넣지 않고, 내부 보고서를 필수 링크로 연결하지 않습니다. 조사 결과에는 관측과 추정, 완료한 검사와 보류한 검사를 구분해 기록합니다.

### 새 안정 버전을 선언할 때

1. `npm run package`로 `release/gtv-v버전.zip`을 만들고 크기·SHA-256을 확인합니다. 태그할 소스로 `scratch/`에 다시 만들어 같은 SHA-256인지 확인합니다.
2. `docs/master-baseline-v버전.md`를 추가합니다. 직전 안정 버전 이후 추가·개선된 기능(항목마다 개발 이력과 같은 분류)과 기준 커밋, ZIP 크기·SHA-256을 적습니다. 기존 기준판 문서와 태그는 고치지 않습니다.
3. 개발 이력에 지정 사실을 적고, 사용자 가이드를 새 안정 버전 기준으로 다시 맞추고, README·개발자 가이드·용어 사전의 현재 안정 버전 표기를 바꿉니다.
4. 선언 커밋에 기준 태그(`v버전`)를 만듭니다.
5. `release/`: 직전 안정 버전과 새 안정 버전 사이의 ZIP을 지웁니다. 지우기 전에 파일 목록과 해시를 `docs_dev/stable/`에 남깁니다.
6. `scratch/`: 새 안정 버전 자체의 검증 증거와 그 이후 기록만 남기고 지웁니다. 지울 목록은 `docs_dev/stable/`에 남깁니다.
7. `docs_dev/`: 새 안정 버전 이전 보고서를 `docs_dev/archive/until-v버전/`으로 옮기고 색인을 고칩니다. 지우지는 않습니다.
